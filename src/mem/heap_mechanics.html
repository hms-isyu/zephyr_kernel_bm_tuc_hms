Chunk, Bucket, Coalesce

A bump allocator moves one pointer. This allocator has no pointer to move. The arena is partitioned into chunks at all times, every chunk carries its own size and its left neighbour's size, and free chunks are threaded onto one circular list per power-of-two size class. Allocating means finding a chunk, possibly cutting it in two. Freeing means welding it back to whichever neighbours are also free.

    The allocation path, in full

    Three probes, then one instruction

    /* alloc_chunk(), heap.c */
bi = bucket_idx(sz);          // floor(log2(units))
b  = &h->buckets[bi];

if (b->next != 0) {
  first = b->next;
  i = CONFIG_SYS_HEAP_ALLOC_LOOPS;   // 3
  do {
    c = b->next;
    if (chunk_size(c) >= sz)   // fits?
      return remove(c, bi);    // hit
    b->next = next_free(c);   // rotate
  } while (--i && b->next != first);
}

bmask = h->avail_buckets & ~BIT_MASK(bi+1);
if (bmask) {
  mb = __builtin_ctz(bmask);  // smallest bucket
  return remove(h->buckets[mb].next, mb);
}
return 0;                      // NULL

    The bounded probe is the whole real-time claim. Three chunks from the exact bucket get tested against the request; if none fits, the fallback takes the head of the smallest strictly larger non-empty bucket, located by one ctz over a 32-bit word. Nothing here scales with the number of free chunks.

    What it costs instead is the work after the search. A chunk from a larger bucket is almost always oversized, so sys_heap_alloc() calls split_chunks() and puts the remainder on a free list. A chunk that fits exactly skips both.

    So the expensive allocation is not the one that searches longest. It is the one that has to cut, and the cheap one is the exact fit taken on the first probe.

    Freeing is the mirror: right_chunk(c) and left_chunk(c) are arithmetic, each is welded on if it happens to be free, and each weld costs one list removal. Then the survivor is added to the bucket for its new, larger size.

    Where the nine sweep sizes land

    request units chunk bytes bucket bucket spans same bucket but too small

    Every sweep size from 32 B up lands exactly one unit above its bucket floor, because the 4-byte header pushes a power-of-two request into the next unit. That makes the adversarial fill trivial to construct: a chunk of S−4 bytes sits in the same bucket as a request for S and is one unit too small to satisfy it. At 4 B and 8 B no such chunk exists, so the miss path cannot be built for those two points.

    Two consequences for the README

    The state axis runs the other way for the heap family. "A heap is slowest when fragmented" holds for an allocator that searches a single free list, but here the fragmented arena is the one state that puts an exact-size chunk on the first probe, while pristine and occupied both pay a split. Occupied is also not a distinct state from pristine: prefilled blocks are used, so they are not in any bucket and the request still falls through to the fallback.

    The one-probe-hit argument against the naive loop needs restating. free_list_add_bidx() inserts at the tail, not the head, so a released chunk is not what the next allocation sees first. The naive loop is still degenerate, for a different and stronger reason: on a pristine arena the released chunk coalesces straight back into the tail remnant, so every iteration replays the same fallback, split, merge triple. The loop is not the best case, it is one fixed case.

    Both are fixable in the builder rather than the design: fill the fragmented state with S−4 blocks instead of S, and the state axis measures what the axis was introduced to measure.

    Modelled on zephyr/lib/heap at the pinned revision, small-heap path: CHUNK_UNIT 8 B, 4-byte header, CONFIG_SYS_HEAP_ALLOC_LOOPS 3, no canaries, no hardening. The stepper runs a port of alloc_chunk, split_chunks, free_chunk and the free-list operations, not an approximation of them.
